# Hold-MCS BLER/OLLA experiment — CARLA no-AE 1 MB payload

Date: 2026-07-27

Purpose: test whether the patched OAI adaptive MCS logic improves the CARLA split-inference uplink without forcing a fixed MCS. The patch keeps adaptive BLER/OLLA active, but when the BLER update window has too few scheduled samples, it holds the previous MCS instead of decrementing it.

## Result summary

Same CARLA no-AE baseline payload: per-channel uint8, ROI 0.0, zstd, about 1.05 MB uplink per frame.

| condition | delivery | median capture→result | median uplink/RAN | median UL MCS | MCS28 share | mean TBS / UL grant | UL grants / run |
|---|---:|---:|---:|---:|---:|---:|---:|
| Ideal loopback | 100.0% | 44.9 ms | 8.4 ms | — | — | — | — |
| OAI 273PRB vanilla adaptive | 85.4% | 212.3 ms | 175.7 ms | 4.0 | 0.0% | 2.1 KB | 681.9k |
| OAI 273PRB hold few-sample MCS | 85.5% | 73.6 ms | 37.5 ms | 28.0 | 98.1% | 12.5 KB | 119.5k |

## Interpretation

- The new hold-MCS adaptive logic removes the high uplink latency for returned frames. Uplink/RAN latency falls from about 176 ms to about 38 ms.
- The hold-MCS run behaves like the fixed-MCS28 diagnostic in latency and scheduler efficiency, while still running the adaptive path.
- The mechanism is visible in UL grant behavior: vanilla adaptive stays around MCS 4 and needs about 682k UL grants; hold-MCS stays near MCS 28 and drains the same app payload with about 120k grants.
- Delivery did not improve materially: vanilla was 85.4%, hold-MCS is 85.5%. Missed frames are 1.5 s result-timeout cases with normal ~1.07 MB feature payloads. So the MCS/backlog latency bottleneck is fixed, but there remains a separate reliability/timeout issue.
- Branch-level `GNB_MAC_BLER_MCS_DECISION.csv` was not extracted for this run, so this result should be presented as behavioral confirmation from actual scheduled UL MCS/TBS/grant traces, not as a branch-count plot.
