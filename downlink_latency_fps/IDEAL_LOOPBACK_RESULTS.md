## Interpretation

> ⚠️ **Codec caveat (2026-07-20): these figures are `--entropy-coder zlib`.** The ~31 ms uplink payload-handling and
> the ~44 ms front are **zlib compress/decompress of the ~1.1 MB no-AE payload**, not wire time. The knob matrix's
> `q_u8_zstd` point puts the same ~1 MB payload at **transport ~7.4 ms / front ~29.8 ms**, i.e. the same no-AE recipe
> under **zstd** should land at **~45 ms capture→result, not ~88 ms**. So the ~88–90 ms below is the *zlib* floor;
> the *zstd* floor (~45 ms) is being confirmed with a live A/B. Codec is a real latency lever, channel-independent.

- Report the Step-1 ideal-loopback headline as **capture/front-start → car result receive ≈ 88–90 ms p50**. The
  `43 ms` value is the subpath from the front's feature-send timestamp to result receive, not the full capture-to-result
  budget.
- The ideal loopback result-return/downlink path is small and stable for this boxes/compact-result path: result payload
  is only about `8–12 KB` and one UDP chunk.
- Result-send to car-receive is about `5 ms` p50 on ideal loopback.
- The residual inside the post-send subpath is about `31 ms` p50. Treat this as feature-upload payload handling
  (UDP burst, reassembly/deserialization/decompression, and local socket/runtime overhead), not RF/channel latency.
- Delivery is `100%` for all FPS points under the raised 8 MB socket-buffer condition.
- The ego route was loaded and autopilot was enabled, but many frames were stopped because the run obeyed lights/traffic on the crowded training route. This is training-like, but the speed columns should be reported so nobody mistakes this for a continuous-high-speed run.

## Component table for reporting

Definitions:

- `front_ms`: front-side model/input prep + feature compression/serialization + current send call.
- `uplink_payload_handling_ms`: post-send residual after subtracting edge tail compute and result downlink. On ideal
  loopback this is **not RF/channel latency**; it is UDP burst/reassembly/deserialization/runtime overhead for the
  ~1.1 MB feature payload.
- `back_ms`: edge tail model/decode path after a complete feature payload is available.
- `downlink_ms`: compact result send-start to car receive; boxes/compact result only.

## FPS-sweep insight

- The latency split is effectively flat across requested FPS. In this synchronous CARLA setup, FPS changes simulation
  tick/radar density per frame, not the model's per-frame payload size.
- Feature payload remains about `1.08–1.09 MB` (`19` chunks) at all FPS because the transmitted tensor shapes are fixed.
- Result payload stays tiny (`~8–12 KB`, `1` chunk), so downlink is cheap for boxes/compact results.
- Radar projected points scale with `200k PPS / FPS`, as expected:

| FPS | radar projected p50 / p95 | feature KB p50 | result KB p50 |
|---:|---:|---:|---:|
| 5 | 38,976 / 39,970 | 1082.8 | 7.8 |

| 20 | 10,000 / 10,000 | 1088.2 | 11.5 |
| 30 | 6,509 / 6,666 | 1081.4 | 9.1 |

This does **not** prove the system can sustain real-time 30 FPS under OAI. The run is synchronous and frame-by-frame;
the next reliability experiment must measure generated FPS, delivered FPS, queueing, drops, and result age over OAI.

## Caveats before report use

- `result_send_to_recv_ms_wall` is a one-way downlink estimate and assumes host clocks are comparable. On loopback this is safe; on OAI, prefer comparing it with `tail_done_to_result_recv_ms` and total RTT.
- The current `capture_to_result_est` is computed from existing logs as `front_ms + round_trip_result_recv_ms`.
  Because the feature-send timestamp is taken just before `sender.send(...)` and `front_ms` ends just after that send,
  this is a conservative estimate that can double-count the feature-send burst. Future runs should log `front_start`
  and `front_send_done` explicitly.
- Headless runs do not populate display-ready fields unless overlay saving or GUI display is enabled.
- The bounded/default-buffer loopback and OAI-default conditions are still pending.
